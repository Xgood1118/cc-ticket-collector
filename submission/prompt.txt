背景：数据团队要把公司内部工单系统的事件数据定期同步到本地分析库。内网有一个分页的 HTTP 查询接口，返回 JSON 格式的工单事件；仓库里已经有一个能跑但只支持全量、直接插入不去重的旧采集脚本，以及建好的 SQLite 库表结构。现在需要在现有基础上做一个可重复运行、支持全量和增量的采集程序，把数据清洗后落库，要求中断后能续跑、不重复也不漏数。仅用 Python 标准库，不引入第三方依赖，不要重写提供数据的接口服务。

任务：
1. 全量采集：分页拉取全部事件并落库。要正确判断分页结束，不能只依赖接口返回的总条数；遇到限流按返回的等待时间退避，服务端临时错误做有限次重试，连续失败超过上限要明确报错退出，不能静默跳过数据。
2. 增量采集：以事件更新时间为水位线，只拉取新增和发生变更的事件。服务端可能出现同一更新时间对应多条、返回顺序乱序、以及更新时间回拨，处理后一条都不能漏，也不能重复入库。
3. 清洗与校验：统一字段命名和时间格式，把嵌套的负责人信息拍平。字段缺失、类型不符、时间无法解析的记录不能丢弃，也不能让主流程中断，要写入隔离表并记录原因，留待人工处理。
4. 落库与去重：按工单业务主键做 upsert，同一工单多次变更只更新不产生新行；增量中被标记删除的工单要在主库同步成已删除状态，不能继续留在有效数据里。
5. 幂等与续跑：记录采集断点，程序在任意阶段被中断后重新运行，要能从断点继续，最终结果与一次完整跑完完全一致，重复运行不产生重复数据。
6. 每次运行结束输出本次统计，包括拉取、新增、更新、删除、隔离的数量；运行仓库内现有测试并补充关键边界用例，确认真实通过，禁止靠删改测试或假设接口永远正常来制造通过。

约束：
- 全程仅用 Python 标准库完成 HTTP 调用、解析和 SQLite 落库，不引入第三方包。
- 保持给定的库表结构和接口调用方式，不要改动提供数据的服务。
- 采集程序要能在命令行以全量或增量两种模式运行；连接地址、库路径等不得写入敏感凭据。
- 所有边界处理（限流、乱序、删除、脏数据）必须能在本机用接口和测试真实复现，不接受只写理论逻辑。
- 所有命令在前台同步执行，不要把命令放到后台运行，也不要启动子代理或额外的审查代理。
